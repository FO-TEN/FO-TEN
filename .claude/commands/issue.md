## 할 일

### 0) 이슈가 정말 필요한지 먼저 판단 — 중요

**이 팀은 모든 작업에 이슈를 만들지 않습니다.** 바로 할 수 있는 일은 브랜치를 파고 PR 로 기록합니다. 아래에 해당할 때만 이슈를 만듭니다.

- **버그** — 재현 절차와 원인을 남겨야 하는 것
- **논의가 필요한 것** — 방식을 정해야 해서 다른 팀원 의견이 필요할 때
- **순서를 맞춰야 하는 것** — BE·FE 가 함께 움직여야 할 때
- **DB 스키마 변경** — 다른 두 명이 각자 재적용해야 하므로 미리 알려야 함
- **미뤄둘 것** — 지금 안 하지만 잊으면 안 되는 일

여기에 해당하지 않으면 **이슈를 만들지 말고**, 그 이유와 함께 `/branch <설명>` 으로 바로 시작하라고 안내한 뒤 멈춥니다.

### 1) 그다음 판단

- 요청이 **버그**인지 **논의/작업**인지 구분합니다.
- 위 열린 이슈 목록에 **중복되는 이슈가 있으면 만들지 말고** 해당 이슈 번호를 알려주고 멈춥니다.
- 내용이 이슈 하나로 쓰기엔 너무 크면 쪼갠 목록을 먼저 제안하고 승인을 받습니다.
- 양식을 채우기에 정보가 부족하면 **추측해서 채우지 말고** 최대 2개까지만 질문합니다.

### 2) 본문 작성

`.github/ISSUE_TEMPLATE/task.yml` / `bug.yml` 의 항목을 따릅니다. **한국어로** 작성합니다.

#### 논의가 필요한 작업

```markdown
## 무엇을
<한 문단>

## 왜 이슈로 올렸는지
<논의가 필요한 지점, 또는 미뤄둔 이유>

## 관련 파트
<be | fe | be + fe | 공통>

## 영향
- DB 스키마 변경이 필요합니다 / 아닙니다
- 다른 팀원 작업과 순서를 맞춰야 합니다 / 아닙니다
- 외부 API(LLM · 환율) 연동이 얽혀 있습니다 / 아닙니다

## 선택지 / 하려는 것
- [ ] <떠오르는 방법. 정해지지 않았으면 비움>

## 참고 자료
```

#### 버그

```markdown
## 증상
## 재현 절차
## 기대 동작
## 실제 동작
## 환경
- 실행 방식: <Docker / 로컬 MySQL / 원격 DB>
- OS / 브라우저:
## 로그 / 에러 메시지
## 추정 원인
```

### 3) 생성

- 제목은 `[작업] 대화 상태 저장 위치 결정` / `[버그] 환율 표시가 하루 밀림` 형태로 만듭니다.
- 본문은 **임시 파일에 쓴 뒤 `--body-file` 로 넘깁니다.** 한국어와 줄바꿈이 셸 이스케이프로 깨지는 것을 막기 위함입니다.

```bash
gh issue create --title "<제목>" --body-file <임시파일> --label "<라벨>"
```

- 라벨은 위 목록에 **실제로 존재하는 것만** 붙입니다. 없으면 라벨 없이 생성하고, 어떤 라벨을 만들면 좋을지 제안합니다.
- 생성 후 이슈 번호와 URL 을 알려주고, `/start #<번호>` 로 작업을 시작할 수 있다고 안내합니다.

### 4) 하지 말 것

- 이슈 본문에 AI 가 작성했다는 서명·꼬리말을 넣기.
- 바로 할 수 있는 단순 작업까지 이슈로 만들기. 이 팀은 그걸 하지 않기로 했습니다.
